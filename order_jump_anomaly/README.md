# order_jump_anomaly

Adds a right-click order: select one or more ships, right-click a **navigation beacon** placed within 5km of an anomaly, and choose "Jump through Anomaly" / "Durch Anomalie springen". The selected ship(s) fly there and are then sent through the anomaly automatically - no manual piloting through the anomaly, and no need to hand-guide a pilot to a precise point in space.

## Why a nav beacon, not the anomaly itself

Anomalies never appear on the map and aren't independently selectable/targetable from the UI, so there is no reliable way to right-click "the anomaly" directly or to send a pilot to its exact (very small) position by hand. Nav beacons (`class.navbeacon`) are the standard, already-existing in-game workaround: the player scans for the anomaly, flies close, and drops a beacon to mark it - which makes the beacon a precise, clickable stand-in for an otherwise unselectable object.

## How it works

- **Menu hook**: `sn_mod_support_apis`' Interact Menu API (`md.Interact_Menu_API`, dependency `ws_2042901274`) is the only available way to conditionally add a right-click action without touching Egosoft's own menu lua. `src/md/order_jump_anomaly.xml`'s `OrderJumpAnomaly_AddAction` listens to `Get_Actions`, checks `event.param.$object.isclass.{class.navbeacon}` and that at least one ship is in `event.param.$selectedplayerships`, then searches for a `class.anomaly` object within 5km (`match_distance`) of the beacon. If found, it registers a new action via `Add_Action` under `$section = 'order'` (not `'interaction'` - confirmed by live testing that a beacon's context menu only renders the `order`-type sections, the same place the native "Fly to and wait"/"Collect Deployable" entries for a beacon show up), passing the found anomaly through as `$echo` so the callback doesn't need to re-search (and risk picking a different one if several anomalies exist in the sector).
- **Sending the ship(s)**: `OrderJumpAnomaly_Callback` fires on selection and spins up one `OrderJumpAnomaly_SendShip` instance per selected ship. Each queues a single custom `JumpAnomaly` order (`aiscripts/order.jump.anomaly.xml`), just appended to the end of whatever the ship's order queue already contains (no `immediate`, nothing cancelled) - a manually clicked-together fly-here/do-that list keeps running first, with "then jump through the anomaly" tacked on at the end.
- **`JumpAnomaly` (`src/aiscripts/order.jump.anomaly.xml`)**: a genuine custom AI order (`<order id="JumpAnomaly">`, `category="navigation"`), not an MD script - structured directly after Egosoft's own `DockAndWait` (`aiscripts/order.dock.wait.xml`). `DockAndWait` also shows as two order-list entries ("Dock"/"Dock and Wait") because it re-checks its own precondition (docked at the right destination?) *every time it (re)starts*, and only if that's unmet does it create an immediate `DockAt` sub-order to fix it - it never assumes a separate, once-only "get there" order already took care of it. This matters because an order that gets interrupted (eg. a manually inserted order runs while it's paused waiting to resume) **restarts from the top of its own script** once it becomes current again - it does not resume mid-flow.

  An earlier version of this mod queued a separate, once-only vanilla `MoveToObject` order in MD ahead of `JumpAnomaly`, and that broke exactly this way once tested live: if the player inserted a manual order between the two, `JumpAnomaly` only checked the ship's position once and could still jump - from wherever the inserted order had since taken the ship, not from the anomaly. `JumpAnomaly` now mirrors `DockAndWait` instead: on every (re)start it checks whether the ship is within `$arrivaldistance` of the anomaly (`this.ship.relativeposition.{$anomaly}.length`), and only if not does it create its own immediate `MoveToObject` sub-order to fly there first (same `<wait exact="1ms"/>` handoff pattern `DockAndWait` uses after creating `DockAt`) - this is also why "Fly to Position" only shows up in the order list when actually needed, rather than being queued unconditionally. `$arrivaldistance` is itself an order param (default only, not user-facing), scaled by the ship's size class exactly like `leap_of_faith_jump_engine_mod`'s `Lib_CorrectShipToDestination` (a bigger ship needs more clearance): 500m (`ship_xs`), 1km (`ship_s`), 2km (`ship_m`), 3km (`ship_l`), 4km (anything else, ie. `ship_xl`).
  - **Pilot skill affects the jump**: once actually near the anomaly, `this.ship.pilot.skill.piloting` (0-15, i.e. 1/3-star steps up to 5 stars - documented in `common.xsd`'s `<skill>` element; a ship with no assigned pilot, eg. the player's own currently-occupied ship, is treated as worst-case skill 0) scales a `<wait min max>` before the transition, using stars (`skill / 3`, 0-5) rather than the raw skill value: `$delaymin = 6 - (skill / 3)` (1s at 5 stars, up to 6s at 0 stars), `$delaymax = 3 * $delaymin` (3s at 5 stars, up to 18s at 0 stars). Mirrors Egosoft's own `aiscripts/move.generic.xml`, which scales a similar post-arrival wait the same way (`<wait max="(...) * (5.1 - (this.ship.pilot.skill.piloting / 3))s"/>`) because a sharper pilot settles in faster.
  - The `$arrivaldistance` proximity check is repeated a third time right after that wait (the order could have been interrupted-and-restarted again during it) before finally calling `perform_gate_transition object="this.ship" gate="$anomaly"` - the same MD/aiscript action Egosoft uses in `scenario_dragonfyre.xml` (`WarpShipsAtGate`) to move ships through a jumpgate/anomaly/highway gate on command. Any of the three checks failing (unreachable destination, ship destroyed, moved away again, etc.) just quietly skips the jump for that pass - the order simply re-validates and tries again next time it's current.
  - The order's map/order-list icon is looked up by an implicit `"order_" + lowercase(id)` naming convention when no explicit `<icon>` is given (eg. `id="MoveToObject"` -> `order_movetoobject`, confirmed in `libraries/icons.xml`); there's no `order_jumpanomaly` icon asset (and no dedicated jump/anomaly/gate order icon in vanilla to reuse under its own name), so without an override it fell back to a "?" placeholder. `<icon name="order_movetoobject"/>` on the `<order>` element fixes this, reusing the same icon already used for the interact menu entry.
  - `JumpAnomaly` carries the full standard interrupt handler set (`SectorChangeHandler`, `TargetInvalidHandler`, `AttackHandler`, `MissileLockHandler`, `ScannedHandler`, `InspectedHandler`, `FoundAbandonedHandler`, `FoundLockboxHandler`, `ResupplyHandler`, `TideHandler`), matching Egosoft's own orders and the Nexus mod "GS QoL: Jump and Wait" (a similar "jump through a gate, then wait" custom order). `SectorChangeHandler` reacts to `this.ship` entering an anomaly/gate - which our own `perform_gate_transition` call triggers - by restarting the order's script from a `<label name="start"/>`; a `$hasjumped` flag (set right before the transition) guards against that restart wrongly re-triggering navigation back to the (now different-sector) source anomaly.

## Known limitation: cannot be used in a repeat order loop

This order cannot currently be added to a player-created repeat order loop. Unlike native orders (`DockAndWait`, `MoveToObject`), it never gets the loop numbering/count in the order list at all - immediately on adding it, before it ever runs. Investigation (live-tested, not guessed) traced this to `ui/addons/ego_interactmenu/menu_interactmenu.lua`, which checks a **native, compiled engine function** (`C.IsOrderLoopable(orderdefid)`) per order id to decide loop eligibility; its internal logic isn't inspectable from any exported script or schema file. Confirmed via live testing to **not** fix it:
- Explicit `allowinloop="true"` on the `<order>` element (schema default is already `true` when omitted).
- Explicitly finishing the order via `cancel_order ... keepinloop="true"` instead of a natural script end (the isolated cause was narrowed down to `perform_gate_transition` itself - the order still gets dropped even when no `MoveToObject` sub-order is involved at all, eg. when the ship starts right next to the anomaly).
- Adding the full standard interrupt handler set (kept anyway, see above - a genuine correctness improvement on its own, just not the fix for this).
- Comparing against `GS QoL: Jump and Wait` (`d:\Spiele\X4 Foundations\extensions\gs_qol_jump_and_wait`, confirmed to loop correctly): its jump order never calls `perform_gate_transition` either - it flies the ship through the gate for real via `move.generic` to a computed position just past the gate's exit (`$targetspace.exit`, `$targetspace.destination.sector`), ie. a normal, physically-simulated transition rather than a scripted teleport. That's not straightforwardly portable to anomalies, which are small enough that reliably flying a ship into one (rather than teleporting it) was the entire reason this mod exists in the first place, and (unlike gates) don't expose a documented destination/exit position to fly toward.

Outside of a loop, the order works normally (one-off use, or appended after other manually queued orders).

## Technical notes

- MD script: `src/md/order_jump_anomaly.xml` (menu hook + queues the order).
- Custom AI order: `src/aiscripts/order.jump.anomaly.xml` (navigate-if-needed + the skill-scaled wait + the actual jump).
- Own texts on a dedicated, collision-free text page `9000002` (distinct from `leap_of_faith_jump_engine_mod`'s `9000001`): `src/t/0001-l044.xml` (English), `src/t/0001-l049.xml` (German) - interact menu action label/mouseover (ids 10/11) plus the custom order's name/description/param label (ids 20-22).
- No changes to any original game files.
- Requires SirNukes' Mod Support APIs (`ws_2042901274` / `sn_mod_support_apis`), see `content.xml`.
- Verified against the actual extracted vanilla/API source under `_modding/export` (including `libraries/aiscripts.xsd`, `libraries/common.xsd`, and real aiscripts like `order.move.wait.object.xml` and `order.dock.wait.xml`) and the plain-text `sn_mod_support_apis/ext_01.dat` (its `.cat`/`.dat` are uncompressed XML, directly greppable) rather than guessed from memory - in particular `perform_gate_transition`, `create_order id="MoveToObject"`, the `<order>` element's own schema (params/requires/location/attention), the "immediate order restarts from the top, not mid-flow" behaviour, the `class.navbeacon` dataset, and the full `Interact_Menu_API` `Get_Actions`/`Add_Action` param docs.
