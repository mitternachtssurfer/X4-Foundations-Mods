# time_to_next_wave

Adds two right-click entries on **Tidebreak** ("Wellenbrecher"), the Riptide Rakers' (`faction.scavenger`, German "Sturmflut-Streicher") landmark station in the Tides of Avarice DLC (`dlc_pirate`):

- **"Time until next tide: 13 minutes"** (or similar) - status only, no click function. The label itself always shows a live snapshot of the current countdown, rounded to the nearest minute (or that a tide is already underway).
- **"Tide Warning: ON/OFF"** - only shown once your reputation with the Riptide Rakers reaches **+10**. Clicking it toggles a standing subscription (not a one-off), independent of the status entry above:
  - **+10 and above**: while toggled on, an incoming message when that tide's `warning` phase starts.
  - **+20 and above**: while toggled on, an additional incoming message the moment the tide actually breaks.

The subscription persists until you toggle it off again - it's rechecked against your *current* reputation every time a phase actually changes, so if you drop below the relevant threshold later, that particular notification just stops firing (without you having to remember to turn it off) and resumes automatically once you qualify again.

## How it works

- **Finding Tidebreak (and the wave itself)**: `TimeToNextWave_Setup` finds the station the same way the DLC's own script does - `find_station_by_true_owner faction="faction.civilian" godstationentry="'pirate_landmark_01'"` (confirmed in `md/setup_dlc_pirate.xml`'s `SetupTidebreakStation`/`TidebreakCondensate` cues; the station's *true owner* is `faction.civilian` even though its resident operator NPC is `faction.scavenger`). The same setup also finds the wave cluster/celestial body (`macro.cluster_500_macro`, `class.celestialbody`) that the two subscription cues below listen on. Guarded to the main galaxy and delayed 1s (same load-order workaround comment as the DLC's own `TheWaveSetup`), and `required="false"` throughout, so the mod is a silent no-op - no menu entries, no notifications - on a save/galaxy without the DLC, rather than erroring.
- **Standing subscription, not a one-shot arm**: `TimeToNextWave_NotifyWarning`/`TimeToNextWave_NotifyWave` are nested *inside* `TimeToNextWave_Setup` (rather than being separate top-level cues) specifically so their `event_object_phase_started object="TimeToNextWave_Globals.$WaveClusterCelestialBody" phase="'warning'"/`'wave'`` conditions only get set up once that variable is actually populated by `TimeToNextWave_Setup`'s own actions - the same nesting reasoning `md.Setup_DLC_Pirate`'s own `TheWaveHandler` uses for `TheWave_StagesProgression`'s phase-watching children. `phase=` on the condition (confirmed in `libraries/common.xsd`'s `event_object_phase_started`, "param = phase string") filters directly to the phase of interest, no manual `event.param` check needed. Each cue fires on *every* real phase transition and does nothing unless `TimeToNextWave_Globals.$NotifySubscribed` is set *and* the current reputation still clears that cue's own threshold (10 for the warning notice, 20 for the wave-start notice) - both re-checked fresh against live state every time, not a snapshot from whenever the player last toggled the setting. Neither cue ever clears the flag itself; it's a standing setting, only ever changed by actually clicking the toggle.
- **The toggle**: `TimeToNextWave_AddAction_ToggleNotify` only adds its action once reputation is 10+ (there's nothing to subscribe to below that), labelled live with `TimeToNextWave_Globals.$NotifySubscribed`'s current state (id 40/41, "ON"/"OFF" - German "AKTIV"/"INAKTIV"). Clicking it runs `TimeToNextWave_ToggleNotify_Callback`, which does nothing but flip that one flag (`set_value .../remove_value ...` - not `exact="not $Var"`, since `$Var?` is an *existence* check in MD, not a truthiness check; a variable explicitly set to `false` would still count as "set" and break the gating in `TimeToNextWave_NotifyWarning`/`_NotifyWave` above, so the flag is either fully removed or set to `true`, never `false`). All the actual reputation/phase gating happens later, independently, whenever the subscribed-to phase change occurs - the callback itself doesn't know or care what reputation currently is.
- **The status entry has no click function**: `TimeToNextWave_AddAction` calls `Add_Action` without a `$callback` at all. Confirmed safe (not an error or a dead reference) by reading `Interact_Menu_API.xml`'s own click handler directly: it only ever signals `$action.$callback` after checking `$action.$callback? and $action.$callback.exists`, so an action with no `$callback` set is simply inert when clicked.
- **Menu hook, gated entirely in `<conditions>`**: both `TimeToNextWave_AddAction` and `TimeToNextWave_AddAction_ToggleNotify` listen to `md.Interact_Menu_API.Get_Actions` (`sn_mod_support_apis`, dependency `ws_2042901274`) with a `<check_value>` sibling condition (not an `<actions>`-level `do_if`) requiring `$object` to be exactly the Tidebreak station found above (no ship selection needed - neither entry is a ship order) - the toggle additionally requires reputation 10+ before it's even added. Both registered under `$section = 'interaction'` (unlike `order_wait_wave`/`order_jump_anomaly`, which use `'order'` for actual ship movement orders) since `Interact_Menu_API.xml`'s own doc comments list `'main'` and `'interaction'` as the two documented section names for this kind of general right-click action - those same doc comments also note `'interaction'` doesn't support a separate `$text2` column (unlike `'main'`), which is why the countdown is baked directly into the status entry's `$text` instead of a second column. (`'interaction'`/`'main'` are also the only two sections a mod can realistically use at all - `menu_interactmenu.lua`'s `config.sections` is a fixed, hardcoded list the game's own render loop iterates over, so no genuinely new/custom section can be created; the rest of that list is either unlabelled or tied to specific vanilla contexts like trade/assignments/player-character interactions.)
- **Live countdown in the status entry**: `TimeToNextWave_ComputeStatusSuffix` computes the current status (the tide's happening now / the remaining time) every single time `Get_Actions` fires - i.e. every time *any* interact menu opens, not just Tidebreak's (though the surrounding `<conditions>` check means this library only actually runs for Tidebreak) - and `TimeToNextWave_AddAction` substitutes it into the label before calling `Add_Action`.
- **Minutes only, not mm:ss**: `TimeToNextWave_FormatMinutes` (shared by `TimeToNextWave_ComputeStatusSuffix` and `TimeToNextWave_ComputeExactText`) rounds the remaining duration to the nearest whole minute - `(($Remaining + 30s) / 60s)i` - and outputs just that plain number (`$Minutes`), rather than a precise mm:ss value. The "N minutes"/"N Minuten" wording itself is inline in each consumer's own text (ids 15/22) rather than a third shared template - with only two short, independently-translatable sentences using it, centralising the rounding *formula* (the part worth not duplicating) was enough; a text-only indirection layer for a two-word phrase wasn't.
- **Reading the wave's real timing**: the Tides of Avarice tide is a genuine engine phase object (`class.celestialbody`, `.phase.current.id` in `calm`/`warning`/`wave`) that `md.Setup_DLC_Pirate.TheWave` drives - the same object `order_wait_wave` already reuses for its own wave-aware orders. That script also precomputes the wave's absolute next start time into `$EndTime_WarningToWave_PhaseStart` (`player.age`-comparable) every time the phase changes (`TheWave_NextStage`), and this is *not* private to that script: `md/story_thefan.xml` itself reads the very same `md.Setup_DLC_Pirate.TheWave.$EndTime_...` variables from entirely outside `TheWave`'s own cue tree - proving these are addressable via `md.Setup_DLC_Pirate.TheWave.$VarName` regardless of how deeply nested (or `instantiate="true"`) the cue that actually set them is. This mod never reimplements or guesses at the wave's timing (durations, randomisation, etc). Only valid while the phase is `calm` or `warning`; during an active `wave` phase this variable still holds the (now past) start time of the *current* wave, which is why the status entry shows "now!" instead of a countdown during that phase.
- **Reputation**: read as `faction.player.relation.{faction.scavenger.relationto.{faction.player}}.uivalue` (the same `.uivalue` conversion pattern used throughout vanilla MD, e.g. `diplomacy.xml`, `story_paranid.xml`), giving the familiar -30..+30 scale.
- **Delivering a notification**: `write_incoming_message`, sourced as `TimeToNextWave_Globals.$TidebreakStation.knownname` (so the sender name shown is Tidebreak's own in-game name, in whichever language the player has installed) - the general "message received by the player" action documented in `libraries/common.xsd`, already used throughout vanilla for reputation/license notifications (e.g. `md/playerreputation.xml`).

## Technical notes

- MD script: `src/md/time_to_next_wave.xml`.
- Own texts on text page `9000004` (distinct from `leap_of_faith_jump_engine_mod`'s `9000001`, `order_jump_anomaly`'s `9000002`, and `order_wait_wave`'s `9000003`): `src/t/0001-l044.xml` (English), `src/t/0001-l049.xml` (German).
- No changes to any original game or DLC files; only reads the DLC's existing celestial body/phase object and its own precomputed timing variables, and finds (never creates or modifies) the existing Tidebreak station.
- Requires SirNukes' Mod Support APIs (`ws_2042901274` / `sn_mod_support_apis`) and, obviously, the Tides of Avarice DLC - deliberately *not* declared as a hard content dependency (same reasoning as `order_wait_wave`), so the mod stays loadable (just inactive) on saves/galaxies without it.
- Verified against the actual extracted DLC source under `_modding/export` (`dlc_pirate/md/setup_dlc_pirate.xml`, `dlc_pirate/md/story_thefan.xml`, `dlc_pirate/libraries/factions.xml`, `08.cat/libraries/common.xsd`, `08.cat/md/playerreputation.xml`, `08.cat/md/story_paranid.xml`, `08.cat/md/terraforming.xml`) and `sn_mod_support_apis`' own `Interact_Menu_API` doc comments (its `.cat`/`.dat` are uncompressed XML, directly greppable) rather than guessed from memory - in particular the Tidebreak station's `godstationentry`, the wave phase object and its cross-script-readable timing variables, the faction id (`scavenger` = Riptide Rakers = German "Sturmflut-Streicher"), the reputation expression and its -30..+30 `.uivalue` scale, `write_incoming_message`'s full attribute set, the click handler's `$callback? and $callback.exists` guard, and the fixed `config.sections` list in `ui/addons/ego_interactmenu/menu_interactmenu.lua`.
